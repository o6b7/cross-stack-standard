# One rule registry is the single source of truth

## Context and Problem Statement

A rule of the Standard is needed in many places: the core skill and its references, path-scoped
rule templates, the managed CLAUDE.md block, the published documentation, the plugin's runtime
(hooks and `doctor` read rule metadata), the fixtures and the gates themselves. If each place
states the rule in its own words, the copies drift, because paraphrase is drift. A common defect
is a rule stated one way in the skill and another way in the docs, with no single text to settle
which is right. The installed plugin is also only a copy of the plugin directory
([0016](0016-self-contained-plugin-runtime.md)), so its runtime cannot read files elsewhere in
this repository.

Where does a rule live, and how do the other places refer to it?

## Decision Drivers

- One authoritative record per rule, readable by scripts.
- Every claim about a rule's gate must be verifiable ([0002](0002-gates-over-guidelines.md)).
- Documentation and runtime data must never be edited by hand into disagreement.
- Rules must be small enough that one fixture can prove one gate.

## Considered Options

- One JSON registry validated by a JSON Schema, with generated documentation and runtime data
- Rules as Markdown files with front matter
- Rules defined in each tool's configuration, with documentation extracted from the configs

## Decision Outcome

Chosen option: "One JSON registry validated by a JSON Schema, with generated documentation and
runtime data", because it is the only option that a dependency-free script can validate, cross-check
against the shipped gates and turn into every other artefact deterministically.

- **Source.** [`registry/rules.json`](../../registry/rules.json), validated by
  [`registry/rules.schema.json`](../../registry/rules.schema.json) (JSON Schema draft 2020-12).
  Fields: `id`, `title`, `track`, `tier`, `module`, `enforcement`, `targetEnforcement`, `gate`
  (`kind`, `id`, optional `discriminator`), `evasions`, `decision`, `defaultEnabled`, `since`,
  `configurable`, `profiles`, a one-sentence `summary`, an `adoption` path, and `invariant` for
  Tier-1 rules. IDs are a prefix (BE, WEB, MOB, SEC, I18N, UI, PROC or CI) and three digits.
- **Tracks.** `track` is `laravel`, `web` or `mobile` for a rule that applies to that track only;
  `client` for a rule that applies identically to both JavaScript client tracks (web and mobile)
  but never to Laravel; and `shared` for a rule that applies to every project. `client` exists so
  a rule shared by the two client tracks is stated once instead of being duplicated per track,
  without wrongly applying it to a Laravel-only project.
- **Granularity.** One rule is one enforceable property, one gate identity and one violation
  fixture. When several rules share one tool rule (for example several selectors of one ESLint
  rule), `gate.discriminator` tells them apart, and two rules may not share a gate identity.
  Rationale lives in the skill references and in decision records, not in the registry.
- **Presence per gate kind.** `scripts/check-registry.mjs` proves that each FORCED or GUARDED gate
  exists: an ESLint rule is registered and enabled in the shipped config; a Pest test or a
  Vitest/Jest test with that title is discovered; a PHPStan rule is registered with that
  identifier; a dependency-cruiser rule with that name exists; a script sub-check is a member of
  the track's check chain; a workflow has that step; a hook event is routed. With
  `--fixture-report` it reads the fixture results: clean passes, violation fails with the rule ID
  printed ([0004](0004-fail-then-pass.md)).
- **Citations.** Skills, docs and templates cite rule IDs and never restate rule text. Every cited
  ID must exist in the registry.
- **Generated copies.** `docs/rules/` is generated by `scripts/generate-rule-docs.mjs`, and the
  plugin's runtime copy under `plugins/cross-stack-standard/data/` by
  `scripts/build-plugin-data.mjs`. Both have a `--check` mode that CI runs, so a hand edit or a
  forgotten rebuild fails.

### Consequences

- Good, because a rule changes in one place and every consumer follows.
- Good, because "claimed but not shipped" becomes a CI failure rather than a review finding.
- Good, because generated counts (FORCED, GUARDED, REVIEW, awaiting promotion) are always true.
- Bad, because JSON is less pleasant to review than prose; the one-sentence `summary` and the
  generated pages compensate.
- Bad, because the fine granularity yields several hundred rules, each needing its own fixture.
- Bad, because presence adapters must be kept in step with each tool's configuration format.

### Confirmation

CI runs `node scripts/check-registry.mjs` (schema, unique IDs and gate identities, gate presence,
violation fixture directories, decision records, citations under `docs/`, the plugin and
`packages/`), `node scripts/generate-rule-docs.mjs --check` and
`node scripts/build-plugin-data.mjs --check`. Whether a rule is split at the right granularity is a
review item.

## Pros and Cons of the Options

### One JSON registry validated by a JSON Schema, with generated documentation and runtime data

- Good, because it is machine-readable with Node.js built-ins and validated by a published schema.
- Good, because every other artefact can be generated from it.
- Bad, because rationale must live elsewhere.

### Rules as Markdown files with front matter

- Good, because prose and metadata sit together.
- Bad, because the prose becomes one more copy to drift from the skill's wording.
- Bad, because front matter across hundreds of files is harder to validate as a whole.

### Rules defined in each tool's configuration, with documentation extracted from the configs

- Good, because the gate and the rule cannot disagree.
- Bad, because REVIEW rules have no configuration to live in.
- Bad, because metadata such as tier, module and decision has no home in an ESLint or PHPStan
  config, and extraction differs per tool.
